PLUGIN & COWORK · ĐÓNG GÓI AGENT

Plugin không phải harness,
nó là cách phát cho cả phòng ban dùng.

Một plugin Claude không tạo ra năng lực mới — nó gói lại những năng lực đã có để người khác cài được. Trang này giải thích plugin nằm ở tầng nào, cách chuyển một hệ 9 sub-agent trong .claude/ thành plugin chạy được trên Cowork, và cái giá phải trả khi làm vậy. Ví dụ xuyên suốt: pipeline nghiên cứu thị trường bảo hiểm nhân thọ (BHNT).

SƠ ĐỒ 01 — XẾP ĐÚNG TẦNG

Plugin và Hermes không cùng một trục

Câu hỏi "plugin có thay thế Agent OS như Hermes không" sai ngay ở giả định: chúng nằm ở hai tầng khác nhau. Plugin là tầng đóng gói — tương đương npm/apt. Hermes là tầng runtime — tương đương chính Claude Code. Bấm vào từng tầng để xem nó gánh việc gì.

Hệ quả cho Agent Spec Generator: plugin không phải khái niệm thứ sáu đứng cạnh Agent / Skill / Orchestrator / Knowledge / Tool. Nó là một render target ở tầng packaging — cùng một bộ spec xuất ra được thành plugin, thành Claude Project, hoặc thành profile Hermes. Hermes là render target ở tầng orchestration. Nếu schema đang gộp hai tầng này vào một trục thì đó là chỗ cần tách.
SƠ ĐỒ 02 — GIẢI PHẪU MỘT PLUGIN

Sáu thành phần, không cái nào là mới

Một plugin chỉ là một thư mục có .claude-plugin/plugin.json cộng với các thành phần đã tồn tại sẵn. Mọi thứ plugin ship được thì bạn đều cấu hình standalone trong .claude/ được. Bấm vào từng ô để xem nó ánh xạ từ đâu và có giới hạn gì.

BẢNG 01 — BA BỀ MẶT, BA MỨC NĂNG LỰC

Cùng một plugin, chạy ở đâu ra kết quả khác nhau

BẢNG 02 — ÁNH XẠ TRỰC TIẾP

Từ .claude/ sang plugin: cái gì đi được, cái gì phải viết lại

Nhìn cấu trúc thật thì việc migrate nhẹ hơn nhiều người nghĩ. Docs ghi rõ: skill nằm ở skills/ hoặc commands/ trong plugin root — skill là thư mục có SKILL.md, command là file markdown phẳng, cả hai đều được tự động phát hiện khi cài. Nên không cần viết lại commands/.

Cấu trúc thư mục đích

research-bhnt/ ├── .claude-plugin/ │ └── plugin.json # "name": "research-bhnt" → namespace ├── commands/ │ ├── pipeline-bhnt.md # → /research-bhnt:pipeline-bhnt │ └── board-review.md ├── agents/ # 9 sub-agent │ ├── market-researcher.md │ ├── product-analyst.md │ └── … ├── skills/ │ └── insurance-fundamentals/ │ └── SKILL.md # rules/ cũ chuyển sang đây └── .mcp.json # nếu cần connector
Đổi tên để tránh đọc lặp. Namespace lấy từ trường name trong plugin.json. Nếu đặt "name": "bhnt" và giữ file pipeline-bhnt.md, lệnh thành /bhnt:pipeline-bhnt — đọc bị lặp. Hoặc đổi file thành pipeline.md để ra /bhnt:pipeline, hoặc đặt "name": "bhnt-research" → /bhnt-research:pipeline.
SƠ ĐỒ 03 — KÍCH HOẠT

Namespace là bắt buộc — và description trở thành giao diện

Mọi skill/command mà plugin ship đều được gọi theo dạng /plugin-name:skill-name. Đây là cái giá cố ý của tầng đóng gói — để hai plugin cùng ship deploy không đè lên nhau. Nhưng bắt một chuyên viên phân tích nhớ chuỗi đó là không thực tế, nên thực tế có ba đường kích hoạt.

1 · GÕ THẲNG
/research-bhnt:pipeline
Chính xác nhưng khó nhớ — chỉ hợp với người đã quen
2 · NÓI TỰ NHIÊN
"chạy nghiên cứu thị trường BHNT quý này"
Claude tự chọn skill dựa trên description — đây mới là đường dùng thật
3 · CLAUDE TỰ GỌI
Trong lúc làm việc, nhận ra ngữ cảnh khớp thì tự kích hoạt
Điểm mấu chốt: khi đóng gói, description chuyển từ "ghi chú cho chính mình" thành giao diện người dùng. Nó là thứ quyết định người non-IT có kích hoạt được pipeline hay không. Hãy đầu tư viết description thật kỹ, coi nó là phần quan trọng nhất của skill chứ không phải metadata phụ.

CÂN ĐO

Được gì, mất gì khi đóng gói

Tóm gọn: plugin không biến người non-IT thành agent architect, nhưng nó biến agent architecture của bạn thành thứ người non-IT dùng được. Bạn thiết kế một lần, cả phòng ban chạy. Đó là đòn bẩy đúng chỗ — miễn là biết rõ mình đánh đổi cái gì.

ĐƯỢC
  • Phân phối thật sự. Hệ 9 sub-agent đang sống trong .claude/ và chỉ mình bạn chạy được — đóng gói xong cả phòng cài rồi dùng ngay từ cuộc hội thoại đầu tiên.
  • Xoá rào cản sử dụng. Chuyên viên không biết code chỉ cần gõ một lệnh, hoặc nói một câu tiếng Việt tự nhiên.
  • Không mất gì về năng lực. Plugin gói lại đúng những thứ đã có: skills, agents, hooks, commands, MCP.
  • Không phải viết code. Orchestration loop, sub-agent, hook lifecycle, MCP — có sẵn, cộng thêm cơ chế phân phối.
  • Version hoá được. Có marketplace, có version — sửa một chỗ, cả team nhận cập nhật.
  • Không đụng namespace. Hai plugin cùng ship deploy vẫn sống chung được.
MẤT
  • Không xoá rào cản thiết kế. Chia scope sub-agent, viết SOP, đặt checkpoint — vẫn là việc kiến trúc, vẫn là bạn làm.
  • Gắn với model Anthropic. Không model-agnostic, không chạy local LLM — đây là khác biệt kiến trúc, không phải khác biệt tính năng.
  • Không sở hữu vòng lặp. Không can thiệp được vào scheduling, retry policy, hay cách context bị cắt. Hook chỉ cho chen vào điểm định sẵn.
  • Không nhúng được vào sản phẩm riêng. Agent phải sống trong UI của bạn, phục vụ người dùng cuối? Cần Agent SDK hoặc harness riêng — plugin không giúp gì.
  • Không có persistence dài hạn. Vượt khỏi session thì tự lo.
  • Cowork ≠ Claude Code. Không terminal, không filesystem tự do, permission model khác. Sub-agent nào dựa vào script hay git phải viết lại.
  • Chi phí token always-on. Plugin cộng token vào mọi session. 9 agent + nhiều skill là con số đáng xem trước khi phát cho cả phòng.
TRƯỚC KHI PHÁT CHO CẢ PHÒNG

Thử tại chỗ, đo chi phí, rồi mới dựng marketplace

Không cần dựng marketplace ngay. Có hai đường thử nhanh và hai lệnh nên chạy sau khi dựng xong.

# Thử tại chỗ — không cần bước cài claude plugin init research-bhnt # scaffold vào ~/.claude/skills/, session sau tự nạp claude --plugin-dir ./research-bhnt # nạp thử trong đúng một session # Hai lệnh nên chạy trước khi phát claude plugin validate ./research-bhnt # bắt lỗi frontmatter claude plugin details research-bhnt # in chi phí token always-on cộng vào MỌI session
Vì sao lệnh thứ hai quan trọng: plugin details là chỗ duy nhất cho bạn thấy plugin này ngốn bao nhiêu token nền ở mỗi cuộc hội thoại — kể cả khi không ai gọi pipeline. Với 9 agent cộng nhiều skill, con số này quyết định plugin nên gói trọn gói hay tách làm hai.
